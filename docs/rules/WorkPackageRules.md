# 工作包规则

适用于 ElymBot 的功能、修复和评测任务。启动流程与用户决策边界见 [AGENTS.md](../../AGENTS.md#工作包流程)。

## 1. 探索与拆包

探索时从产品入口追到实际实现、构建配置和测试。验证会影响范围、行为或验收的关键前提，记录代码位置、实际运行结果和无法验证的条件。将需要用户决定的问题连同影响和建议一起交给用户，供其确定任务书。临时探针及设备证据可保存在本地 `探索/` 或 `验证/`。

用户交付任务书后，总控保留原文，引用探索证据，只补查影响拆包的变化或缺口。拆包使用已确认的目标和标准。任务书交付执行后，由总控按依赖启动 Worker。用户只授权拆包时，实施等候后续授权。

## 2. 目录与编号

`docs/work/` 的直接子目录保存活跃工作包。`TXX` 用于功能或工程任务，`FXX` 用于修复，`BXX` 用于评测。沿用用户指定编号。用户未指定时，按同前缀下一个可用编号创建，并同时检查活跃目录与 `docs/work/archive/`。任务书和目录使用相同的编号和简称。

```text
docs/work/TXX-任务名称/
├── TXX-任务名称.md
├── TXX-任务名称-spec.md
├── TXX-任务名称-tasks.md
├── TXX-任务名称-checklist.md
├── prompt/
│   ├── W01-职责名称-prompt.md
│   └── W02-职责名称-prompt.md
└── feedback/
    ├── W01-职责名称-feedback.md
    └── W02-职责名称-feedback.md
```

原任务书随包保存。每个 Worker 使用一对同名编号的 Prompt 和 Feedback，Feedback 在实际执行后建立。单负责人任务使用一个 Worker，复杂度和实际依赖决定分组。完成的工作包由用户决定何时移入 `docs/work/archive/`，保持原编号和目录名。

## 3. Spec · 交付边界

写明背景、目标、交付能力、关键行为与架构约束、范围外事项和验收标准，引用相应的探索证据和用户决定。文件级实施细节写入 Tasks。设置「能力欠账」一节，列出因后置能力尚未实现而明确暂缓的部分与回补条件。无欠账时写「无」。

## 4. Tasks · 实施顺序

文件顶部列 Worker 分组、组内顺序和组间依赖。按实际写入范围确定接口和共享文件的负责人及交接时点。每项写任务编号与名称、目标、改动文件及职责、前置依赖、参考位置、完成边界与验证入口。

收尾明确正式入口接入、端到端验证与被替代路径的清理。端到端验证使用该任务真实交付入口。文档工作包核对读者入口、链接和交付内容。产品工作包从 App 或插件实际入口覆盖正常路径和关键失败路径。

## 5. Checklist · 可观测验收

按 Tasks 的编号、名称和顺序列核对项。每项写验证对象、方法、可观察的通过条件和证据位置，并对应任务书的验收要求。通过条件须能判定，避免只写「功能正常」或「测试充分」。只有完成验证且满足条件的条目才勾选。需要用户实测的项目根据实际反馈勾选。

正式入口接入、端到端验收和清理可以引用前序仍有效的证据。同一次验证可以覆盖多个验收项，Feedback 记录命令、结果和对应项。尚未覆盖的必需验收必须完成。后续只在改动使证据失效、检查失败或仍有具体未解决问题时，补充或重跑受影响的检查。必需验收通过后停止验证。

## 6. Worker Prompt · 执行指令

每份 Prompt 应能脱离聊天记录独立执行。列出负责的任务及顺序、前置依赖、必读资料、已定的接口、可改和禁止修改的范围、Checklist 条目、反馈路径与交接条件。公共规则通过文件引用复用。跨模块共享文件按已约定的负责人和时点修改。范围外事项及待拍板方案不写成执行指令。

## 7. Feedback · 结果与返工

记录实际改动、关键实现决定、文件或产物、实际执行的验证及其结果、覆盖的 Checklist 项、已知限制和待验事项。注明命令或操作、环境或设备、产物版本和可定位证据。区分源码、构建、自动化、合成输入、模拟器、真机和用户验收。

总控审查工作区差异、实际入口和证据，集成影响证据有效性时复验相应路径。返工、用户反馈和复验按日期或轮次追加到原 Feedback，写清原因、修复和结果，保留此前记录。Feedback 以审查所需内容为限，范围外发现记录影响后交总控处理。交付时汇总产物、最短验收步骤和未完成条件。

总记录按 [AGENTS.md 的工作记录规则](../../AGENTS.md#工作记录) 登记。

## 8. 实施冻结与状态

首次按 Worker Prompt 实施时，原任务书、Spec、Tasks、Prompt 和 Checklist 的条目内容冻结。Checklist 可以更新勾选状态，Feedback 可以追加。发现依据冲突或需要变更目标、范围、公共边界或验收标准时，记录证据和影响，按 AGENTS.md 的决策规则处理。用户决定变更后，由总控按授权更新工作包基线，再分派受影响部分。

拆包或重拆时核对活跃与归档目录，并维护 [工作包状态](../Context-Index.md#current-status) 全量清单。包级验收对照实际交付、源码、Checklist 与 Feedback 更新当前包状态。新建、部分实施或验收项未闭合的包使用 `not_implemented`。交付已落地、Checklist 全部完成且 Feedback 有证据的包使用 `implemented_unarchived`。用户完成归档后使用 `archived`。

拆包时核对 [能力欠账](../OutstandingDebtList.md)，登记新增条目、更新回补条件、删除已回补条目。一般范围外需求、未证实设想和当前应修复的缺陷仍按其原有性质处理。
