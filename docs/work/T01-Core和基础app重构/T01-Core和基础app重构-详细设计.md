# T01-Core 和基础 App 重构详细设计

本文细化 [T01 任务书](T01-Core和基础app重构.md)的实现与验收。原生界面以 [高保真原型 v0.6.3](ElymBot_高保真原型.html)为准。批量删除、并行回复、应用内新消息提示及图片位置调整按任务书补齐。当前仓库已有启动页、Core Gradle 模块以及 QQ、定时任务 AAR 骨架，以下是目标设计。文中的数据表、接口方法和参数默认值是实现建议，可在拆包时按实际依赖调整。

## 1. 首版交付能力

| 归属 | 首版交付 | 用户或验收者能看到的结果 |
| --- | --- | --- |
| Core · 会话执行 | 单一宿主 Agent、顺序 ReAct、停止、超时、执行上限、按预算装配与压缩 | 同一轮可先读历史再继续回答。主会话切换人格后沿用同一历史。专属会话始终使用归属人格。 |
| Core · 模型 | OpenAI 兼容的模型列表、探测、文本回复、视觉直答和图片转述、原生流式和非流式、结构化工具调用 | App 能按主模型实际能力选择调用方式，真实增量在服务完成前显示。 |
| Core · 指令和工具 | 五个固定指令行为、自定义指令名、`HistoryRead`、工具注册和调用边界 | `/help` 显示当前名称和行为。通过编号切人格或回退，模型可读取压缩前仍保留的历史。 |
| 基础 App · 人格和聊天 | 原型的人格库、搜索筛选、编辑与封面、全局主会话、人格专属会话、文字和图片输入、历史、流式气泡、停止和失败重试 | 新装 APK 可从人格页进入聊天，关闭重开后仍可继续。指令和工具反馈沿用纯文本交互。 |
| 基础 App · 配置和数据 | 模型服务管理、三项能力探测、主模型和视觉模型用途分配、指令改名、Room 本地数据及凭据存取 | 配置重启后可用。回退后消息和检查点实际删除。 |
| 插件底座 | 宿主装配和工具来源登记，统一描述、启用筛选、调用、反馈、取消契约，构建隔离 | 用内置 HistoryRead 和测试来源通过同一条工具链验收。基础 APK 无需安装插件，实际 APK 和依赖图不含 QQ 或定时任务实现。 |

原型已有页面按其结构、视觉层级和入口落地。平台、插件导航按原型保留禁用态。设置入口本期仅服务于指令改名。深浅色、语言、应用更新、备份恢复、诊断和缓存管理等跟随之后的原型。应用内独立 Bot 档案已取消。插件底座的具体交付口径见第 8 节。

专属会话由主会话菜单进入对应人格列表，沿用原型的首条消息入列、最近活动排序、改名和返回行为。批量删除从当前人格列表进入多选，确认后删除选中会话。原型的运行限制和检查点演示以任务书中的并行生成、固定空点、回退删尾和五项指令行为为准。

## 2. 从 App 到模型的链路

1. Compose 将发送、停止、重试、配置和指令改名动作交给 ViewModel。ViewModel 显示 Room 中的会话历史与当前运行状态；运行由 App 会话服务在进程内按会话持有，页面只订阅相应会话。Compose 或 ViewModel 离开时结束订阅，正在运行的请求继续接收增量。重新订阅时从该会话的当前状态读取已累积内容。
2. 会话服务解析 Slash Command，命中时执行本地操作。普通输入校验模型、附件和凭据可用性，然后保存用户消息并创建执行中的轮次。按当前会话的人格 ID 读取最新配置，该轮捕获人格内容、模型用途、能力、当前可用工具和历史边界。修改人格后从下一轮起使用新配置。
3. Core 根据所用模型组装请求，通过模型适配器获取文本增量或结构化工具请求。执行中的文本只更新本轮气泡。最终状态和消息由 App 会话服务写回。
4. 按会话 ID 串行判定发送、重试、建点、回退和主会话人格切换。消息与执行事件始终归属发起轮次的会话。不同会话可同时运行，每个会话最多一个活动轮次。增量、完成和失败事件按会话 ID 和尝试 ID 路由，最终消息在原会话提交。停止只取消目标会话的执行。建点、回退和删除只检查目标会话的运行状态。数据库事务只包本地写入，不跨网络等待。

## 3. 本地存储与生命周期

使用 App 私有 Room/SQLite 存储结构化数据。下表给出主键和查询边界，字段名可随实现调整。

| 数据 | 主要字段和关系 | 读写用途 |
| --- | --- | --- |
| 会话 | 稳定会话 ID、类型、人格 ID、当前检查点 ID、下一个单调递增的轮次序号 | 主会话初始化一次，人格 ID 表示可切换的激活人格。专属会话的人格 ID 为固定归属，入口按人格 ID 查询。每个会话创建时初始化各自的空检查点，删尾后该会话的序号继续递增。 |
| 轮次 | 会话 ID、稳定序号、用户消息、最终状态、开始和结束时间、实际人格和模型显示信息 | 状态含运行中、完成、停止、中断。按会话和序号查找，唯一键为会话加序号。 |
| 消息 | 轮次 ID、轮内顺序、角色、文本、附件引用、类别 | 正常消息供历史和模型装配。助手工具反馈供聊天展示。失败残片可见并带状态。 |
| 附件 | 所属消息、私有文件名、类型与大小 | 聊天图保存在 App 私有文件目录。人格封面使用独立归属。数据库持有引用。 |
| 检查点 | 稳定 ID、会话 ID、可复用显示编号、边界轮次序号、创建时间 | 显示编号按当前顺序。固定空点编号 1，边界为 0。 |
| 历史摘要 | 会话 ID、起止轮次序号、摘要正文和创建时间 | 覆盖所属会话的连续、已完成轮次。有效摘要按顺序且互不重叠。 |
| 人格、模型和指令 | 人格内容、封面引用、服务标识和 Base URL、模型 ID、探测结果、用途、指令名称 | App 负责读写。探测与具体服务地址和模型绑定。变更连接配置时将相关结果恢复为未探测。 |
| 凭据 | 服务 ID 对应私有加密记录 | Android Keystore 管理加密密钥，App 私有存储保存密文。换地址时重新确认对应凭据。Key 仅用于认证。 |

原始对话、摘要和检查点各自保存。会话完成新回复时更新持久化的消息位置或未读状态。会话未打开时收到的新回复提示在对应会话条目，打开并看到回复后清除。人格保存封面与头像各自的相对位置，渲染按实际裁剪框应用，调整其中一项时保留另一项的设置。

删除专属会话时，由会话服务校验归属和运行状态，再在同一事务删除所选会话及其轮次、检查点、摘要和附件引用。正在生成的所选会话先结束或停止，再执行删除。提交后清理无引用私有文件。删除人格时重新检查其名下会话及主会话运行状态。按原型保留至少一个人格，删除主会话激活人格时选用另一人格，继续原主会话历史。模型请求从本地记录临时装配。工具结构化调用和原始返回值留在活动轮次内存中；对话历史保存最终助手回复以及需要留在聊天里的助手反馈。压缩工具结果使用本轮内存里的观察摘要。恢复进程时把残留运行中状态结为中断，避免假定模型仍在回复；仍在内存的流式草稿可能丢失。用户主动停止或正常收到中断时提交已显示文本和状态。重试复用原用户消息，并用新执行结果替换它的失败回复。

导入文件先写入 App 私有目录，数据库提交引用后才成为有效附件。回退事务先删引用，提交后清理无引用私有文件；清理中断时可从有效引用重算孤儿文件。用户相册原件由系统相册管理。文件访问和历史读取均以有效记录为入口。

## 4. 指令与检查点事务

- 指令注册固定行为 ID 和默认名称。App 保存每个行为当前名称，校验名称非空、无空格且无重复。Core 按首个空格分开名称和参数，按当前名称查找行为。帮助和列表用 App 字符串资源生成。主会话切人格时取人格列表编号。检查点编号只在当前会话内解析。专属会话只提供该会话可用的指令行为。无效指令或参数给出本地反馈。
- `/mark` 在最后一个已完整结束的轮次后建点。若尾部有停止或中断的轮次，它们不作为新边界。创建时计算下一个显示编号，并更新当前检查点。普通聊天只追加轮次。
- `/checkpoint N` 查编号，`/reset` 取当前点。两者共用同一 Room 事务入口，所有查询和删除均限定会话 ID。事务内确认目标仍属于当前会话，删除边界之后的轮次及其消息、附件引用，删除结束位置超出边界的历史摘要，删除目标点之后的检查点，并更新当前点。摘要跨边界时整条删除，保留侧原文仍在。提交失败时原历史与当前点同时保留。
- 回到 1 后当前会话、人格及模型设置继续可用，其他会话保持各自的历史、摘要和检查点。删除结果提交后再显示简短回执。下一次建点可复用显示编号，内部 ID 和轮次序号继续使用稳定标识。
- 例子。点 2 锚定 A、B，点 3 锚定 A、B、C、D。回到 2 后，C、D、旧点 3 和覆盖 C 或 D 的摘要一起移除。聊 E、F 后建的新点 3 对应 A、B、E、F。选择空点 1 删除其后的全部对话。

参考 Re-UthCode 的 [稳定 transcript 范围](D:/project/Re-UthCode/src/uthcode/core/history.py#L302)、[提交边界](D:/project/Re-UthCode/src/uthcode/core/history.py#L499)和[指令解析](D:/project/Re-UthCode/src/uthcode/application/commands/parser.py#L32)。其 ActiveCheckpoint 用于摘要提交。T01 的检查点是用户可选的会话删除边界，删除由 App 落盘。

## 5. 上下文、压缩和 HistoryRead

### 5.1 请求装配和预算

每次主模型请求前按如下顺序装配。宿主规则和生效人格在前，其后是必要的运行信息、历史摘要与未被覆盖的完整轮次、本次用户消息、仍有效的本轮工具调用与结果。工具定义通过协议工具字段传递。摘要、图片转述和工具内容保留各自来源，作为上下文材料。只在请求需要时加入时间和时区。未完成历史、指令回执、工具展示文本由 App 按各自类别保存或展示，默认不重复投影成模型历史。

历史图片的原件供聊天查看。视觉转述产生的文字随所属轮次保存，后续可用文字与引用装配历史。视觉直答轮次保留原问题和回答，历史附件默认带引用，需要重发图片时仍按本次模型能力和预算决定。图片转述、历史摘要和附件引用随所属数据一起失效或删除。

预算基于本次所用模型的已知窗口。按窗口扣除输出预留及估算误差余量后，计入消息结构、提示词、工具定义、工具结果和图片，再选择历史。优先使用可得的模型计量规则，缺少精确计量时用保守估算。64K 是现有架构的选型基线。对未知窗口使用可配置的保守默认值，实际超限时最多进行一次压缩或裁剪后重试。最新用户输入与还在使用的工具调用及结果优先保留。

### 5.2 压缩步骤

1. 在首次请求前和每次工具结果回填后检查预算。接近输入上限或服务明确报上下文超限时，按由早到晚选择完整历史轮次作为第一批，保留最近完整轮次。历史仍不足时，可选本轮较早且调用与结果均已完成的工具批次，保留最新批次。
2. 用当前主模型发起有界摘要请求。摘要调用使用独立短提示和非流式结果，仅提交选定材料，不带工具定义、不进入 Agent 循环。摘要保留结论、用户约束、来源或消息引用、失败状态和未决事项。历史摘要的覆盖边界由宿主赋值。
3. 校验覆盖范围仍有效、摘要有正文，与候选摘要重装一次正式请求并重新计量。确认占用下降才提交。相邻的既有摘要需一起压缩时，替换记录与新摘要在同一事务提交。本轮工具观察摘要随本轮使用，成对移出较早的调用及对应结果，保持协议中的剩余调用和结果闭合。
4. 重装并再次检查预算。不同工具批次后允许再触发，同一份未变化材料只尝试一次，整轮受时间与压缩次数上限控制。摘要失败或没有降幅时保留之前的有效摘要，先从最旧的可选历史裁剪。必要材料仍超限则结束并提示。原始历史由 Room 保留，裁剪和摘要只改变模型请求。
5. 初始调参建议集中在 Core，使用可注入预算做验收。建议以输入预算约八成触发压缩，保留最近两个完整轮次，每轮最多三次摘要，压缩与模型续轮共用轮次总时限。实现阶段按定向测试确定具体值。

### 5.3 HistoryRead

- 工具范围由宿主绑定当前会话。建议参数为 `fromTurn`、`toTurn`、`limit`，均针对稳定轮次序号。缺省读取最近一页，指定范围时返回范围内按序排列的原文。结果含实际范围、可继续读取的边界和截断标记。压缩摘要附覆盖范围，模型可以据此定向回读。
- 从 Room 分页读取仍保留的用户与助手文本，按页数和 Token 预算限制输出，图片仅返回有意义的附件引用或已有文字描述。读取的范围不接受会话 ID 或文件路径。已删除范围返回无记录，失败返回受控结果。
- App 通过窄的历史读取接口向 Core 提供查询。Core 注册工具说明、校验参数、执行和回填。助手文本反馈走运行事件，结构化结果按调用 ID 留给模型继续处理。重复回读仍受同一轮预算和工具执行上限控制。

## 6. ReAct、模型与流式交付

### 6.1 单轮执行

```text
装配请求并检查预算
→ 读取模型响应，同时发布可见文本增量
→ 结束时确认本次响应的类型
  ├─ 普通回答 → 交付最终消息与状态
  └─ 完整工具批次 → 按顺序校验和执行
                     → 按调用 ID 回填每个结果
                     → 重新装配并检查预算
                     → 下一次模型调用
```

轮次内只有 Agent 写执行状态。模型适配器负责读取协议，工具返回值和 App 动作通过事件传递。工具批次只有完整接收并确认响应终止后才可运行。未知工具、无权限、参数不合法和普通执行失败分别返回受控结果。仍有后续调用时保留原顺序，取消停止后续执行。失败和拒绝也回填一个与调用对应的结果。首版可先按最多 8 次主模型调用、16 次工具调用、单次工具读取 10 秒和整轮 180 秒作为定向验收的建议默认值，测试通过注入较小上限验证退出。工具阶段的简短反馈由助手身份显示在原型气泡里。最终回复、执行失败、取消和超时都有可观测状态。

参考 Re-UthCode 的 [即时文本投影](D:/project/Re-UthCode/src/uthcode/core/agent.py#L2257)、[顺序工具执行](D:/project/Re-UthCode/src/uthcode/core/agent.py#L2834)、[工具反馈](D:/project/Re-UthCode/src/uthcode/core/agent.py#L3207)和[结果回填](D:/project/Re-UthCode/src/uthcode/core/agent.py#L3276)。

### 6.2 适配、探测与图片

- 使用同一个 OpenAI 兼容适配器调用 `GET /models` 和 `POST /chat/completions`。模型 ID 可手填。连接、认证和接口响应错误分别映射为可展示状态。主模型、视觉模型各引用具体服务和模型。
- 三项探测分别用简短文本、带已知内容的测试图片、开启流式的短文本。流式成功需要有效 SSE 文本增量与有效终止。普通 JSON 或服务明确报告不支持时记录对应能力；认证、限额、网络、异常响应和截断记作未确认。内部保留结构化工具能力状态，以所选模型的已知能力或可控的结构化调用探针确定，界面验收仍是三项。普通对话在工具能力未确认时可用，HistoryRead 验收用已验证支持结构化工具的模型。

### 6.3 SSE 与 Compose

- 已支持的模型发送 `stream: true`。适配器从响应体逐帧解码 UTF-8，根据空行切分 SSE 事件，合并同一帧的多个 `data:` 行。忽略注释和仅计费事件。正文增量保持原空格和换行，收到即可交给 Core。分别处理正文、工具增量和终止原因。 [SSE 解析规范](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) · [Chat Completions 流式事件](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)
- 工具增量按调用 `index` 累积，关联收到的 ID，按片拼接参数字符串。响应终止后校验调用结构。缺失 ID、重复 ID 或截断的批次作为协议错误处理。可定位到调用 ID 的参数错误返回对应工具结果。提前 EOF 或有错误事件时将当前请求标为中断。允许正常结束事件加 `[DONE]`，或已经收到明确结束事件后正常 EOF。输出达到模型上限时保留文字并标明截断，截断的工具批次不执行。已知不支持流式的模型用 `stream: false`，按普通完整响应解析，仍可按能力处理结构化工具。
- 链路为适配器增量 → Core 文本事件 → App 会话状态 → Compose 当前气泡。App 追加到同一气泡，可按帧合并刷新，首段无需等最终结果。停止向上传播取消并关闭响应体，晚到事件按执行 ID 丢弃。半截保留，正常结束后提交完整文本。普通 JSON 回包或中途断开已有流式输出时，按对应状态反馈。探测未确认时先用普通回复，并允许用户复测。
- 参考原型的 SSE 读取、Re-UthCode 的增量交付与终止校验，以及旧 ElymBot 的网络层读取。旧 ElymBot App 交付层等待完整结果后切段。T01 按会话将网络增量交给当前气泡。 [原型 SSE 读取](ElymBot_高保真原型.html#L1466) · [Re-UthCode 增量发出](D:/project/Re-UthCode/src/uthcode/integrations/providers/openai_compat.py#L509) · [流终止校验](D:/project/Re-UthCode/src/uthcode/core/provider.py#L1304) · [旧 ElymBot 网络层](C:/Users/93445/Desktop/Astrbot/ElymBot-Android-Native/app/src/main/java/com/elymbot/android/core/runtime/llm/ChatCompletionService.kt#L2705) · [旧 App 交付层](C:/Users/93445/Desktop/Astrbot/ElymBot-Android-Native/feature/chat/runtime/src/main/java/com/elymbot/android/feature/chat/runtime/AppChatRuntimeService.kt#L171)

## 8. 插件底座

T01 的建议交付线是 **宿主侧可扩展、工具来源可替换、基础 APK 独立构建**。HistoryRead 是验证这条链路的首个实际工具，随 Core 交付。下载、安装、装载用户侧独立插件属于接下来的交付边界；若 T01 还需要验收装入外部制品，须先确定制品格式、加载进程和生命周期，因为这些决定将改变任务范围。

| 职责 | T01 设计 |
| --- | --- |
